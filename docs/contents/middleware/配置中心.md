# 配置中心

## 简介

配置中心是微服务架构中集中管理应用配置的基础设施组件，支持配置的动态推送和版本管理。微服务时代服务数量多、环境多（开发/测试/预发/生产），把配置散落在各个服务的本地文件里会带来一系列问题：

- 修改一个配置要逐台机器改、逐个重启，效率低且容易漏改；
- 配置与代码一起打包，调整参数就要重新发布；
- 多人多环境修改配置容易互相覆盖，出错后无法追溯和回滚；
- 数据库密码等敏感配置散落各处，难以统一管控。

配置中心把配置从应用中剥离出来，集中存储、统一管控、动态生效。

## 核心功能

- 配置集中管理
- 动态配置推送
- 配置版本管理
- 灰度发布
- 配置回滚

### 配置集中管理

所有服务的配置统一存储在配置中心，按 **环境（Environment）→ 应用（App）→ 配置集/命名空间（Namespace）** 的层级组织，配合权限控制做到"谁能看、谁能改"可控。

### 动态配置推送

配置修改后**无需重启应用**即可生效。两种实现机制：

| 机制 | 原理 | 时效 |
|------|------|------|
| 长轮询 / 长连接 | 客户端挂起请求，服务端配置变更时立即返回 | 秒级 |
| 定时轮询 | 客户端周期性拉取比对 | 取决于轮询间隔，分钟级 |

典型场景：动态开关（降级开关、活动开关）、限流阈值、日志级别在线调整。

### 配置版本管理

每次修改生成新版本，记录修改人、修改时间、修改内容 diff，支持按版本查看历史。

### 灰度发布

配置变更先对**部分实例**生效（如指定 IP 列表或一定比例的节点），观察无异常后再全量发布，降低错误配置的影响面。

### 配置回滚

发现配置有误可一键回滚到任一历史版本，配合版本管理实现"改错能秒级恢复"。

## 常见方案

### Nacos

阿里开源，**配置中心 + 注册中心二合一**，是 Spring Cloud Alibaba 生态的标配。

- **配置模型**：Namespace（环境隔离）→ Group（分组）→ Data ID（通常命名 `${spring.application.name}-${profile}.${yaml|properties}`）；
- **推送机制**：客户端长轮询（默认 30s 挂起），配置变更秒级感知；本地有快照缓存，Nacos 服务端宕机不影响应用使用最后一次配置；
- **动态刷新**：Spring 中用 `@RefreshScope` 或 `@ConfigurationProperties` 自动感知变更；
- **存储**：支持内嵌 Derby（单机）和外置 MySQL（生产推荐）。

```yaml
spring:
  cloud:
    nacos:
      config:
        server-addr: nacos.example.com:8848
        namespace: dev            # 环境隔离
        file-extension: yaml
```

```java
@RestController
@RefreshScope // 配置变更时刷新该 Bean
public class LimitController {
    @Value("${order.limit:100}")
    private int orderLimit;
}
```

### Apollo

携程开源的专用配置中心，功能完善、治理能力强，适合配置管理要求高的中大型团队。

- **配置模型**：App → Env（环境）→ Cluster（集群/机房）→ Namespace（配置集，分 private/public）；
- **架构**：Portal（管理界面）+ Admin Service（配置读写）+ Config Service（客户端拉取，长轮询通知）+ MySQL 存储；
- **亮点**：完善的权限审批流程、发布审核、灰度发布、实时生效、客户端本地文件缓存兜底、修改历史与回滚；
- 相对 Nacos 更重（组件多、部署复杂），但不依赖注册中心能力，职责更纯粹。

### Spring Cloud Config

Spring 官方最早的配置中心方案，**以 Git 仓库作为配置存储**：

- Config Server 从 Git 拉取配置并通过 HTTP 暴露；客户端启动时拉取；
- 配置即文件，天然享受 Git 的版本管理、Code Review、审计能力；
- **动态刷新较弱**：需要客户端暴露 `/actuator/refresh` 端点手动触发，或配合 Spring Cloud Bus + MQ 广播刷新；
- 无自带管理界面，高可用需自己保障（多实例 + 负载均衡）；
- 适合配置变更频率低、习惯 Git 工作流的团队；在国内微服务实践中已逐步被 Nacos/Apollo 替代。

```yaml
# Config Server
spring:
  cloud:
    config:
      server:
        git:
          uri: https://git.example.com/config-repo.git
```

### ZooKeeper

ZK 本身是分布式协调服务，并非专门的配置中心，但早期常被"兼职"使用：

- 配置以 znode 形式存储，客户端通过 **Watch 机制**监听节点变化，变更实时通知；
- 优点：通知实时性好、组件常见（Dubbo/Hadoop 生态常已部署）；
- 缺点：**无管理界面、无版本管理、无权限审批**，Watch 是一次性的需要重复注册，大配置受 znode 1MB 大小限制；
- 现代架构中不建议把 ZK 当配置中心，更适合做分布式锁、Leader 选举等协调场景。

## 选型对比

| 维度 | Nacos | Apollo | Spring Cloud Config | ZooKeeper |
|------|-------|--------|--------------------|-----------|
| 定位 | 配置中心 + 注册中心 | 专用配置中心 | 配置中心 | 分布式协调（兼职） |
| 实时推送 | 长轮询，秒级 | 长轮询 + 通知，秒级 | 需手动/Bus 刷新 | Watch，实时 |
| 管理界面 | 有 | 完善（权限/审批/灰度） | 无 | 无 |
| 版本管理/回滚 | 支持 | 完善 | 依赖 Git | 弱 |
| 灰度发布 | 支持（Beta 发布） | 支持 | 不支持 | 不支持 |
| 存储 | MySQL / Derby | MySQL | Git | znode（1MB 限制） |
| 部署复杂度 | 低 | 高（多组件） | 低 | 中 |
| 生态 | Spring Cloud Alibaba | 通用 | Spring Cloud | Dubbo/Hadoop |
| 适用场景 | Spring Cloud Alibaba 技术栈 | 配置治理要求高的大中型团队 | 轻量/变更少的场景 | 已有 ZK 的协调场景 |

## 设计考量

### 配置热更新

配置"能推送"只是第一步，应用"正确响应"才是难点：

- **刷新方式**：Spring 中 `@RefreshScope` 重建 Bean、`@ConfigurationProperties` 重新绑定；也可以监听配置变更事件自定义刷新逻辑；
- **原子性与一致性**：多个配置项联动时（如分子/分母），要保证一次性生效，避免读到"半新半旧"的组合；
- **幂等与校验**：变更回调可能重复触发，新值要做合法性校验（非法值宁可保留旧值并告警）；
- **注意不可热更的配置**：数据源连接池、线程池大小、端口等启动时确定的资源，热更需重建资源，要评估是否值得支持。

### 配置安全

- **敏感信息加密**：数据库密码、密钥等必须加密存储（Nacos 支持配置加密插件，Apollo 可对接 KMS，或 Jasypt 应用层加密）；
- **权限隔离**：按环境、按应用划分读写权限，生产配置修改需审批，开发人员默认只读生产；
- **审计与脱敏**：所有变更记录操作人与内容；日志打印配置时注意脱敏；
- **客户端兜底**：配置中心不可用时应用要能启动——使用本地缓存快照或默认值，启动顺序上不要让配置中心成为强依赖死锁点。

### 高可用

配置中心是所有应用的启动依赖，必须高可用部署：

- **集群部署**：至少 3 节点，前置负载均衡；Nacos 集群依赖 MySQL 主备，Apollo 各组件多实例；
- **多机房容灾**：配置数据跨机房同步（Apollo 支持多机房部署，各机房独立 Config Service）；
- **客户端容灾**：本地文件缓存最后一次配置，服务端全挂时应用仍能以旧配置运行/重启；
- **变更风控**：生产配置变更走灰度 + 快速回滚预案，错误配置的影响往往比服务宕机更广（一次推送全量生效）。

## 与 K8s ConfigMap 的关系

Kubernetes 原生的 **ConfigMap / Secret** 也能承载配置，与专业配置中心是互补而非替代关系：

| 对比项 | K8s ConfigMap | 专业配置中心 |
|--------|---------------|--------------|
| 定位 | 基础设施层的配置注入 | 应用层的配置治理 |
| 交付方式 | 环境变量 / 挂载文件 | SDK 拉取 + 推送 |
| 变更生效 | 挂载文件更新有延迟，环境变量需重启 Pod | 秒级推送，代码内直接刷新 |
| 治理能力 | 弱（依赖 GitOps 工具链） | 强（权限、审批、灰度、审计） |
| 适用内容 | 基础设施参数、启动脚本、不变的环境变量 | 业务开关、阈值、频繁调整的参数 |

常见分工：**环境级、不常变的配置放 ConfigMap/Secret（配合 GitOps 管理）；业务级、需要动态生效和治理的配置放配置中心**。云原生场景下也有 Nacos/APISIX 等直接对接 K8s 的集成方案。
