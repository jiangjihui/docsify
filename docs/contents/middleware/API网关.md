# API 网关

## 简介

API 网关是微服务架构中的统一入口，负责请求路由、协议转换、限流熔断等横切关注点。所有客户端请求都先经过网关，再由网关转发到后端的具体服务。

在微服务架构中，后端被拆分为几十甚至上百个服务，如果没有网关，客户端会面临以下问题：

- 需要知道每个服务的地址，管理大量服务入口；
- 每个服务都要各自实现认证、限流、日志等重复逻辑；
- 跨域、协议转换等问题在每个服务中重复处理；
- 无法对内部服务做统一的安全防护。

网关就像一个大楼的**前台**：所有来访者（请求）先到前台登记（认证）、被引导（路由）到对应的房间（服务），前台还负责安保（安全防护）和访客记录（日志监控）。

## 核心功能

- 请求路由
- 负载均衡
- 限流与熔断
- 认证与授权
- 协议转换
- 日志与监控

### 请求路由

路由是网关最基础的能力：根据请求的路径、Header、参数等条件，将请求分发到对应的后端服务。成熟的网关还支持**动态路由**——路由规则存储在配置中心或数据库中，修改后无需重启即可生效。

除了基础路由，网关通常还支持：

- **重写（Rewrite）**：转发前修改请求路径，如 `/api/user/1` → `/user/1`；
- **重定向**：返回 301/302 跳转到新地址；
- **灰度路由**：按用户 ID、Header、流量比例将部分请求导向新版本服务。

### 负载均衡

网关在将请求转发到后端服务的多个实例时，需要按一定策略分配流量：

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 轮询（Round Robin） | 依次分发 | 实例性能均匀 |
| 加权轮询 | 按权重比例分发 | 实例配置不同 |
| 最少连接 | 转发给当前连接数最少的实例 | 请求处理时长差异大 |
| 一致性哈希 | 按 Key 哈希到固定实例 | 会话保持、缓存命中 |

在微服务场景下，网关通常与**注册中心**（Nacos、Eureka、Consul）集成，自动感知服务实例的上下线，无需手动维护地址列表。

### 限流与熔断

网关是流量的第一道关口，是实施流量治理的最佳位置。

**限流**：防止突发流量压垮后端服务，常见算法：

| 算法 | 原理 | 特点 |
|------|------|------|
| 固定窗口 | 单位时间内计数，超过阈值拒绝 | 实现简单，有窗口临界突刺问题 |
| 滑动窗口 | 将窗口细分为多个小格子滑动统计 | 平滑，精度更高 |
| 漏桶 | 请求入桶，以固定速率流出 | 流量绝对平滑，无法应对突发 |
| 令牌桶 | 匀速放令牌，请求需拿令牌才能通过 | 允许一定程度的突发流量，最常用 |

限流维度可以是全局、单路由、单用户、单 IP 等；分布式场景下通常基于 Redis 实现集群限流。

**熔断**：当下游服务错误率过高时，网关快速失败（短路），避免请求堆积拖垮整个链路。熔断器一般有三种状态：关闭（正常放行）→ 打开（直接拒绝）→ 半开（放行少量请求探测恢复情况）。

### 认证与授权

将认证逻辑收敛到网关，后端服务就无需重复实现：

1. **统一认证**：校验请求携带的 JWT / OAuth2 令牌，验证通过后把用户信息（如 userId）写入 Header 透传给下游；
2. **权限校验**：粗粒度的访问控制（如 `/admin/**` 只允许管理员），细粒度权限建议留在业务服务中；
3. **黑白名单**：按 IP、应用标识拦截恶意来源。

> 典型链路：客户端携带 Token → 网关验签并解析 → 附加 `X-User-Id` 等 Header → 转发到下游服务 → 下游服务信任网关传递的身份信息。

### 协议转换

客户端与后端服务的协议往往不一致，网关负责在边界做协议适配：

- **HTTPS 卸载**：对外 HTTPS，对内 HTTP，TLS 加解密开销集中在网关；
- **WebSocket**：将长连接请求转发到支持 WebSocket 的后端；
- **gRPC-HTTP 转码**：把外部 REST 请求转换为内部 gRPC 调用；
- **Dubbo / 私有协议**：将 HTTP 请求转换为 Dubbo 等 RPC 协议调用（如 APISIX 的 dubbo-proxy 插件）。

### 日志与监控

所有流量都经过网关，是天然的数据采集点：

- **访问日志**：记录请求路径、耗时、状态码、来源 IP，用于审计和排查；
- **指标监控**：QPS、延迟分布（P99）、错误率，接入 Prometheus + Grafana；
- **链路追踪**：生成或透传 TraceId，串联起完整调用链（配合 OpenTelemetry / SkyWalking）。

此外，**请求聚合**也是常见功能：一次客户端请求由网关并发调用多个后端服务，将结果合并返回，减少客户端请求次数（多用于移动端弱网环境）。

## 常见方案

### Nginx

Nginx 是高性能的 HTTP 服务器和反向代理，基于事件驱动的异步架构，单机轻松支撑数万并发连接，是流量入口层最常见的选择。

```nginx
upstream user_service {
    server 10.0.0.1:8080 weight=5;
    server 10.0.0.2:8080;
}

server {
    listen 443 ssl;
    location /api/user/ {
        proxy_pass http://user_service;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

- **优点**：性能极高、稳定性经过大规模验证、部署简单；
- **缺点**：原生能力偏静态，修改配置需要 reload；动态路由、限流等高级能力需要借助 **OpenResty**（Nginx + LuaJIT）二次开发；与服务注册中心的集成较弱。

> Nginx 常被用作最外层流量入口（四层/七层负载均衡），与专业 API 网关组合使用：Nginx 负责接入层，网关负责业务路由和治理。

### Kong

Kong 基于 OpenResty（Nginx + Lua）构建，是开源 API 网关的代表之一，采用插件化架构。

- **架构**：分为数据面（Data Plane，处理请求流量）和控制面（Control Plane，管理配置），数据面依赖 PostgreSQL / Cassandra 存储配置（也支持 DB-less 声明式配置）；
- **插件生态**：内置认证（JWT、OAuth2、Key Auth）、限流、日志、链路追踪等数十个插件，也支持自定义 Lua / Go / Python 插件；
- **管理方式**：通过 Admin API 或图形化控制台管理路由与插件。

```bash
# 创建一条路由，指向 user-service
curl -X POST http://localhost:8001/services/user-service/routes \
  --data "paths[]=/api/user" \
  --data "name=user-route"
```

- **优点**：插件丰富、开箱即用、社区生态成熟，有企业版（Kong Enterprise）提供管控台；
- **缺点**：Lua 二次开发门槛较高，重度依赖外部数据库。

### Spring Cloud Gateway

Spring Cloud Gateway 是 Spring 官方的网关组件，用于替代基于 Servlet 阻塞模型的 Zuul 1.x。它建立在 **Spring WebFlux + Netty** 之上，采用异步非阻塞模型。

**核心概念**：

| 概念 | 说明 |
|------|------|
| Route（路由） | 网关的基本构建块：ID + 目标 URI + 断言 + 过滤器 |
| Predicate（断言） | 匹配条件，如 Path、Header、Method、Query、时间 |
| Filter（过滤器） | 对请求/响应做修改，如 StripPrefix、AddRequestHeader、限流 |

**配置示例**（yml 方式）：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: user-service
          uri: lb://user-service        # lb:// 表示从注册中心负载均衡
          predicates:
            - Path=/api/user/**
          filters:
            - StripPrefix=2             # 转发前去掉前两段路径
            - name: RequestRateLimiter  # 基于 Redis 的令牌桶限流
              args:
                redis-rate-limiter.replenishRate: 10   # 每秒生成 10 个令牌
                redis-rate-limiter.burstCapacity: 20   # 桶容量 20
```

**编码方式**：

```java
@Bean
public RouteLocator customRouteLocator(RouteLocatorBuilder builder) {
    return builder.routes()
        .route("user-service", r -> r.path("/api/user/**")
            .filters(f -> f.stripPrefix(2))
            .uri("lb://user-service"))
        .build();
}
```

- **优点**：与 Spring Cloud 生态（Nacos/Eureka、Sentinel、OpenFeign）无缝集成，Java 团队开发维护成本低；
- **缺点**：性能低于 Nginx/APISIX 等 C/Lua 系网关；动态能力依赖 Spring Cloud 生态组件。

### APISIX

Apache APISIX 是 Apache 顶级项目，同样基于 OpenResty，但设计上更现代化，主打高性能与动态化。

- **架构**：数据面基于 Nginx/Lua 处理流量，配置存储在 **etcd** 中，路由变更毫秒级生效，**无需 reload**；
- **全动态**：路由、插件、证书、上游都可通过 Admin API 热更新；
- **插件热加载**：内置 80+ 插件（限流、熔断、认证、可观测性等），支持插件热加载和按路由绑定；
- **多协议**：HTTP/HTTPS、gRPC、WebSocket、Dubbo、MQTT、TCP/UDP 四层代理。

```bash
# 创建路由：/api/user/* 转发到上游，并启用限流插件
curl -X PUT http://127.0.0.1:9180/apisix/admin/routes/1 \
  -H "X-API-KEY: admin-key" \
  -d '{
    "uri": "/api/user/*",
    "upstream": {
      "type": "roundrobin",
      "nodes": {"10.0.0.1:8080": 1}
    },
    "plugins": {
      "limit-req": {"rate": 10, "burst": 20, "key_type": "var", "key": "remote_addr"}
    }
  }'
```

- **优点**：性能业界领先（官方数据可达数万 QPS/核级别）、完全动态、社区活跃、Dashboard 完善；
- **缺点**：引入了 etcd 依赖，运维复杂度略高；Lua 自定义插件有一定门槛。

> Apache APISIX 的路由 / 上游 / 插件配置模型与限流插件参数详解见 [APISIX](/contents/microservice/APISIX.md)。

### 方案对比

| 特性 | Nginx | Kong | Spring Cloud Gateway | APISIX |
|------|-------|------|---------------------|--------|
| 技术栈 | C | OpenResty（Nginx + Lua） | Java（WebFlux + Netty） | OpenResty（Nginx + Lua） |
| 性能 | 极高 | 高 | 中等 | 极高 |
| 动态配置 | 弱（需 reload/OpenResty） | 较强（依赖数据库） | 强（配合配置中心） | 强（etcd 毫秒级生效） |
| 插件生态 | 弱（需自研） | 丰富 | 中（Filter 机制） | 丰富（80+ 内置插件） |
| 服务发现集成 | 弱 | 支持多种注册中心 | Spring Cloud 生态原生集成 | 支持多种注册中心 |
| 适用团队 | 运维团队 | 通用 | Java / Spring Cloud 团队 | 追求高性能与动态化的团队 |
| 典型定位 | 流量接入层 | 业务网关 | 业务网关 | 业务网关 / 云原生网关 |

## 与 BFF 的区别

BFF（Backend For Frontend，服务于前端的后端）是位于网关与后端服务之间、**为特定前端定制**的一层，由 Sam Newman 在《Building Microservices》中提出。

动机：不同客户端（Web、App、小程序）对同一后端数据的需求差异很大——App 需要精简字段省流量，Web 需要完整字段，小程序又需要另一种聚合方式。如果在后端服务中兼容所有端，服务会变得臃肿；因此为每种前端单独建一层做数据裁剪和聚合。

| 对比项 | API 网关 | BFF |
|--------|---------|-----|
| 定位 | 全端统一入口，流量边界 | 面向特定前端的适配层 |
| 数量 | 通常一个（或按内外网分） | 每类前端一个（Web BFF、App BFF…） |
| 职责 | 路由、认证、限流等横切关注点 | 数据聚合、裁剪、编排等适配逻辑 |
| 业务逻辑 | 几乎不包含 | 包含面向展示的业务编排 |
| 维护方 | 平台 / 基础架构团队 | 前端 / 业务团队 |
| 稳定性要求 | 极高（全站入口） | 相对独立，故障影响面小 |

> 实践中二者常组合使用：**网关 → BFF → 微服务**。网关只做通用治理，BFF 做面向端的业务聚合。如果只有一个前端或各端需求差异不大，BFF 并非必需。

## 设计考量

### 网关与业务边界

网关的核心原则：**只处理横切关注点，不承载业务逻辑**。

适合放在网关的能力：

- 路由、认证、限流、熔断、日志监控、协议转换、跨域处理、灰度分流。

不应该放进网关的内容：

- **业务编排与数据聚合**：这是 BFF 或业务服务的职责。一旦网关混入业务逻辑，每次业务迭代都要改网关，网关从"稳定基础设施"退化为"业务变更瓶颈"；
- **复杂的权限判断**：网关只做粗粒度校验，细粒度的资源权限应在业务服务内完成；
- **数据库 / 缓存的重操作**：网关位于每个请求的关键路径，重操作会显著放大延迟。

### 性能与延迟

网关位于所有请求的关键路径上，**每增加 1ms 延迟都会被全量流量放大**，性能设计要点：

1. **异步非阻塞 I/O**：选择 Netty（Spring Cloud Gateway）、Nginx/epoll（APISIX、Kong）等非阻塞模型，避免一请求一线程的阻塞模式；
2. **连接复用**：网关到后端服务使用长连接 / 连接池，避免每请求三次握手和 TLS 开销；
3. **配置本地缓存**：路由、证书、限流规则等配置在本地缓存，避免每请求远程查询；
4. **插件轻量化**：网关插件逻辑应尽量轻量，重逻辑（如查数据库鉴权）考虑异步化或下沉到服务侧；
5. **合理的超时与重试**：设置连接超时、读超时，重试仅对幂等请求生效，防止重试风暴。

### 高可用部署

网关是全站的单点风险所在，必须按最高可用级别部署：

1. **无状态化**：会话、限流计数等状态外置到 Redis，网关实例本身无状态，才能随意水平扩容；
2. **多实例 + 前置负载均衡**：网关自身部署多实例，前面再挂一层 LVS / 云 SLB / F5 做四层层负载；
3. **优雅上下线**：发布时先摘流量再停机，配合无损下线避免请求报错；
4. **配置热更新**：路由变更不应重启网关（APISIX 的 etcd 方案、Kong 的 DB 同步、Spring Cloud Gateway 配合配置中心）；
5. **故障隔离与降级**：网关自身要有降级预案（如配置拉取失败时使用本地缓存的兜底配置），避免"网关挂了全站挂"；
6. **多机房容灾**：网关随业务做多机房 / 多可用区部署，流量可一键切换。
