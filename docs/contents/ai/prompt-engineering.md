# 提示词工程

## 概览

即使模型能力再强，**怎么说（prompt）** 极大影响输出质量。提示词工程（Prompt Engineering）就是研究"如何设计输入，让 LLM 稳定产出我们想要的结果"的学科。

它不需要改模型权重，仅靠调整提示即可泛化到多数任务，是成本最低、见效最快的 LLM 优化手段，也是 Agent、RAG、工具调用等高级用法的共同底座。

```
   你写的提示 (Prompt)
   ┌─────────────────────────┐
   │ 角色 + 任务 + 上下文 + 格式 │
   └─────────────────────────┘
              │
              ▼
         LLM 生成
              │
              ▼
      期望的高质量输出
```

> 前置阅读：[LLM 基础](/contents/ai/llm-basics.md)。更深入的 Agent 级提示编排见 [AI Agent（智能体）](/contents/ai/ai-agent.md)。

### 什么是提示词工程？

提示词工程是**通过结构化地设计输入文本，引导模型输出符合预期结果**的实践。它把"模糊的需求"转写为模型能稳定理解的指令。

为什么重要：

- 同一模型，好提示与差提示的产出天差地别。
- 在多数业务场景，提示优化比微调模型更便宜、更快、更易迭代。
- 它是 Function Calling、RAG、多 Agent 协作的"接口层"。

### 基础原则

无论哪种任务，以下原则普遍有效：

1. **清晰具体**：避免歧义，明确"做什么、给什么、产出什么"。
2. **给足上下文**：提供必要的背景、目标读者、约束条件。
3. **指定角色（Role）**：用"你是一位资深 X"设定语气与专业度。
4. **明确输出格式**：要求 JSON / 表格 / 固定模板，便于程序解析。
5. **拆成步骤**：复杂任务用"先…再…最后…"降低模型出错率。
6. **设边界与示例**：给出正例（Few-shot）与"不要做什么"。

> 经验法则：把模型当成一个**能力强但不了解你业务细节的新同事**，把任务交代清楚。

### 核心技法

| 技法 | 说明 | 适用场景 |
|------|------|----------|
| **Zero-shot** | 直接给指令，不给示例 | 通用、模型已擅长的任务 |
| **Few-shot** | 在提示里放 2~5 个（输入, 输出）范例 | 特定格式、风格、分类边界 |
| **Role / System Prompt** | 设定身份与总体规则 | 统一语气、约束行为 |
| **Chain-of-Thought (CoT)** | 要求"逐步思考"再给答案 | 推理、数学、多步逻辑 |
| **Self-Consistency** | 多次采样取多数投票 | 提升推理稳定性 |
| **ReAct** | 推理（Thought）+ 行动（Action/工具）交替 | Agent、工具调用 |
| **Step-back Prompting** | 先问抽象高层问题再答具体 | 复杂、需第一性原理的问题 |
| **Tree-of-Thought** | 多分支探索并回溯择优 | 需要搜索/规划的任务 |

**Chain-of-Thought 示例**：

```
请逐步推理，再给出最终答案。
问题：一个班 32 人，男生比女生多 4 人，女生几人？
步骤：设女生 x 人，则男生 x+4 人；x + (x+4) = 32 → 2x = 28 → x = 14。
答案：女生 14 人。
```

### 结构化输出与格式约束

让模型输出**机器可解析**的结果，是接入业务系统的关键：

- **JSON 模式**：要求只返回 JSON，并用 schema 约束字段。
- **分隔符**：用 `###` / `"""` 等明确包裹不同区块，便于正则切分。
- **Function Calling**：把"调用哪个函数、参数什么"交给模型结构化输出（见 [AI Agent](/contents/ai/ai-agent.md)）。

```python
# 用 LangChain 的 PromptTemplate 固化提示结构
from langchain_core.prompts import PromptTemplate

prompt = PromptTemplate.from_template(
    "你是一位资深{role}。\n"
    "任务：{task}\n"
    "要求：只输出 JSON，字段为 {{answer, reason}}。\n"
    "输入：{input}"
)
print(prompt.format(role="分析师", task="判断情感", input="服务很好"))
```

### 提示词模板与变量化

在生产中，提示不应硬编码，而要**模板化 + 变量注入**，便于版本管理与 A/B：

- 用 `PromptTemplate`（LangChain）、Jinja2、或简单 f-string 管理。
- 把"系统规则 / 上下文 / 用户问题"分层拼接，避免互相污染。
- 把 Few-shot 示例抽成独立数据集，与模板分离维护。

### 常见陷阱

| 陷阱 | 表现 | 改进 |
|------|------|------|
| 指令模糊 | 输出跑题、格式错 | 明确任务 + 输出格式 |
| 信息过载 | 重点被淹没 | 精简、加分隔、分步骤 |
| 缺示例 | 风格/边界不对 | 加 Few-shot |
| 忽略格式 | 无法程序解析 | 指定 JSON/模板 |
| 未设边界 | 模型越权或胡编 | 加"只做 X、不知则说不知" |
| 温度过高 | 事实类任务不稳 | 事实问答调低 temperature |

### 提示词的评估与迭代

提示词也是"代码"，需要可评估、可回归：

1. **建测试集**：覆盖典型与边界 case 的（输入, 期望输出）集合。
2. **定指标**：准确率、格式合规率、人工打分、与标杆的相似度。
3. **做对照**：不同提示版本跑同一测试集，量化差异。
4. **版本化**：把提示当作资产入库（Git / LangSmith 等），便于回滚。

> 当提示已很复杂仍不稳定，往往说明该上 **RAG**（补知识）或 **Agent/工具**（补能力）了，见本分类对应文章。
