# 分布式事务

## 简介

分布式事务是在分布式系统中保证多个服务间数据一致性的事务机制。当业务操作涉及多个数据源时，需要分布式事务来保证要么全部成功，要么全部回滚。

典型场景：电商下单要同时**扣减库存（库存服务）+ 创建订单（订单服务）+ 扣减余额（账户服务）**，三个操作分属不同服务和数据库，本地事务无能为力。

分布式事务没有银弹——CAP 定理决定了强一致与可用性不可兼得，因此各种方案本质都是在**一致性强度、性能、业务侵入性**之间做权衡。

## 本地事务回顾

### ACID

单机数据库事务的四大特性，是理解分布式事务的基石：

| 特性 | 含义 | 实现机制 |
|------|------|----------|
| **原子性（Atomicity）** | 事务内的操作要么全做，要么全不做 | undo log（回滚日志） |
| **一致性（Consistency）** | 事务前后数据满足业务约束（如转账前后总额不变） | 由 AID 共同保证 |
| **隔离性（Isolation）** | 并发事务互不干扰 | 锁 + MVCC |
| **持久性（Durability）** | 提交后的修改永久生效 | redo log + WAL（先写日志再落盘） |

MySQL InnoDB 通过 **redo log（重做，保证持久性）+ undo log（回滚与 MVCC，保证原子性和隔离性）+ 两阶段提交（redo 与 binlog 一致）** 实现 ACID。

### 事务隔离级别

并发事务会引发三类问题：**脏读**（读到未提交数据）、**不可重复读**（同一事务内两次读取结果不同）、**幻读**（同一查询范围内行数变化）。四种隔离级别从低到高逐级解决：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|----------|------|-----------|------|------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 几乎不用 |
| READ COMMITTED（读已提交） | 解决 | 可能 | 可能 | Oracle 默认，每次读取最新快照 |
| REPEATABLE READ（可重复读） | 解决 | 解决 | 可能* | **MySQL InnoDB 默认**，*通过 MVCC + 间隙锁（Gap Lock）基本解决幻读 |
| SERIALIZABLE（可串行化） | 解决 | 解决 | 解决 | 读加共享锁，并发度最低 |

> 隔离级别越高并发性能越低，绝大多数业务使用 RC 或 RR 即可；分布式事务讨论的"一致性"与这里的隔离级别"一致性"不是同一概念——前者指多副本/多服务的数据一致，后者指并发可见性。

## 分布式事务方案

### 2PC（两阶段提交）

由**事务管理器（协调者，TM）** 统一协调多个**资源管理器（参与者，RM）** 提交：

- **阶段一：Prepare（准备/投票）**
  - 协调者询问所有参与者"能否提交"；
  - 参与者执行本地事务但**不提交**，写 redo/undo 日志，锁定资源，回复 Yes/No；
- **阶段二：Commit/Rollback（提交/回滚）**
  - 所有参与者都回复 Yes → 协调者发 Commit 指令，参与者提交；
  - 任一参与者回复 No 或超时 → 协调者发 Rollback，全部回滚。

**XA 协议**是 2PC 在数据库层面的标准接口（`XA START / XA END / XA PREPARE / XA COMMIT`），MySQL、Oracle 等数据库原生支持；JTA（Java Transaction API）是 Java 侧的事务规范，Seata XA 模式、Atomikos 均基于此。

**优点**：强一致性，对业务无侵入（数据库层面完成）。

**缺点**：

- **同步阻塞**：Prepare 后参与者持锁等待 Commit，期间资源被锁定，吞吐严重下降；
- **单点问题**：协调者宕机后，参与者可能一直阻塞在 Prepare 完成状态（不知道该提交还是回滚）；
- **数据不一致风险**：阶段二协调者发出部分 Commit 后宕机，部分参与者已提交、部分未收到。

### 3PC（三阶段提交）

在 2PC 基础上改进，把 Prepare 拆成两步，并引入超时机制：

- **CanCommit**：协调者只询问"能否执行"，参与者不执行事务、不锁资源，仅做可行性检查；
- **PreCommit**：检查通过后参与者执行事务但不提交（同 2PC 的 Prepare）；
- **DoCommit**：真正提交。

改进点：参与者引入**超时默认提交**——PreCommit 阶段后若迟迟收不到 DoCommit，参与者超时后自行提交，避免协调者宕机导致永久阻塞。

**局限**：超时默认提交在网络分区时反而可能造成不一致（协调者决定回滚，参与者却超时提交了），且仍是同步阻塞。3PC 理论意义大于实践，**工程中几乎没有落地**。

### TCC（Try-Confirm-Cancel）

业务层面的两阶段方案，把一个操作拆成三个业务接口：

| 阶段 | 含义 | 示例（转账 100 元） |
|------|------|---------------------|
| **Try** | 资源检查与预留 | 冻结账户 100 元（余额不动，冻结字段 +100） |
| **Confirm** | 确认提交，使用预留资源 | 从冻结金额中扣除 100 元 |
| **Cancel** | 取消，释放预留资源 | 解冻 100 元 |

**必须处理的三个异常问题**：

1. **幂等**：Confirm/Cancel 可能被重试调用，必须幂等（可用事务状态表记录事务分支状态）；
2. **空回滚**：Try 因网络原因未到达，Cancel 先到了——Cancel 要能识别"没 Try 过"并直接返回成功；
3. **悬挂**：Cancel 先执行后，迟到的 Try 又执行了，资源被永久预留——Try 要检查是否已经 Cancel 过，是则拒绝执行。

**优点**：不依赖数据库锁，Try 阶段只预留业务资源，性能好、一致性较强。

**缺点**：业务侵入大（每个服务都要写三个接口），设计成本高。

**适用场景**：对一致性和性能要求都高、资金类核心业务（支付、转账、账务）。

### SAGA

长事务方案：把大事务拆成一系列本地事务 T1 → T2 → ... → Tn，**每个 Ti 配套一个补偿操作 Ci**；任一步失败，按序反向执行已完成步骤的补偿（C(n-1) → ... → C1）。

**两种实现模式**：

| 模式 | 原理 | 优缺点 |
|------|------|--------|
| **编排式（Choreography）** | 各服务通过事件驱动：T1 完成后发事件触发 T2，失败发补偿事件 | 无中心组件、解耦，但流程分散在事件里，链路复杂时可读性差 |
| **协调式（Orchestration）** | 中心协调器（Saga Orchestrator）按定义好的流程逐步调用各服务 | 流程集中可视、易维护，协调器本身需要高可用 |

**特点**：

- 无锁、无资源预留，适合**长流程、跨多服务**的业务（旅行预订：机票 + 酒店 + 租车）；
- **隔离性弱**：中间状态对外可见（已扣款未发货），需要业务上防"脏读"（如状态标记、语义锁）；
- 补偿不是万能的：已发出的短信、已出的票可能无法补偿，需要人工处理或调整执行顺序（把不可逆操作放最后）。

### 本地消息表

基于**最终一致性**的可靠异步方案，利用本地事务保证"业务操作"与"消息记录"的原子性：

1. 服务 A 在**同一个本地事务**中：执行业务操作 + 往本地消息表插入一条待发送消息；
2. 后台任务（定时/MQ）扫描消息表，把消息投递给下游（或发到 MQ）；
3. 服务 B 消费消息执行操作，**消费必须幂等**（消息可能重复投递）；
4. B 处理成功后回调/通知 A 标记消息为已完成（或靠定时对账兜底）。

**优点**：实现简单、可靠性高（本地事务兜底）、天然异步解耦削峰。

**缺点**：最终一致（有延迟）、消息表与业务耦合、需要定时任务和对账机制。

### 消息事务

用消息中间件的事务能力替代本地消息表，把"消息可靠投递"的复杂度交给 MQ：

- **RocketMQ 事务消息**
  - 生产者发送**半消息（Half Message）**，对消费者不可见；
  - Broker 确认后，生产者执行本地事务；
  - 根据本地事务结果向 Broker 提交（Commit，消息可见）或回滚（Rollback，丢弃消息）；
  - 若 Broker 长时间未收到二次确认，**主动回查**生产者的本地事务状态（`TransactionListener#checkLocalTransaction`）。

```java
TransactionMQProducer producer = new TransactionMQProducer("tx-group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            orderService.createOrder(arg); // 执行本地事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // Broker 回查：根据业务单号查本地事务状态
        return orderService.exists(msg.getKeys())
                ? LocalTransactionState.COMMIT_MESSAGE
                : LocalTransactionState.UNKNOW;
    }
});
```

- **基于 Kafka 的实现**
  - Kafka 0.11+ 支持**幂等生产者**（`enable.idempotence=true`，防重复写）和**事务 API**（`initTransactions / beginTransaction / commitTransaction`）；
  - 典型用法是 **consume-transform-produce** 原子化：消费 → 处理 → 生产 + 提交 offset 在一个事务中，实现 exactly-once 语义（配合 `read_committed` 消费端）；
  - Kafka 事务定位是**流处理场景的精确一次**，不是通用分布式事务方案，跨异构数据库的场景不适用。

## 常见框架

### Seata

阿里开源的分布式事务解决方案，定义了三方角色：**TC**（事务协调器，独立部署）、**TM**（事务管理器，定义全局事务范围，通常是发起方）、**RM**（资源管理器，管理分支事务资源，各参与服务）。

使用方只需 `@GlobalTransactional` 一个注解：

```java
@GlobalTransactional(rollbackFor = Exception.class)
public void placeOrder(OrderDTO dto) {
    orderService.create(dto);        // 本地操作
    storageClient.deduct(dto);       // 远程：扣库存
    accountClient.debit(dto);        // 远程：扣款
}
```

**四种模式**：

| 模式 | 原理 | 侵入性 | 一致性 | 适用 |
|------|------|--------|--------|------|
| **AT** | 自动生成 undo log：一阶段拦截 SQL 记录前后镜像并提交本地事务，二阶段异步删除 undo（提交）或用前后镜像反向补偿（回滚） | 无侵入 | 最终一致（默认隔离下中间态可见） | 绝大多数 CRUD 业务，默认选择 |
| **TCC** | 手写 Try/Confirm/Cancel | 高 | 较强 | 高性能核心链路 |
| **SAGA** | 状态机驱动正向执行 + 反向补偿 | 中（定义补偿） | 最终一致 | 长流程、遗留系统集成 |
| **XA** | 标准 XA 两阶段提交，连接持锁到二阶段 | 无侵入 | 强一致 | 对一致性要求极高、并发不高的场景 |

**选型口诀**：优先 AT（简单）→ 性能不够换 TCC（核心链路）→ 流程长用 SAGA → 强一致低并发用 XA。

## 选型建议

### 强一致性 vs 最终一致性

| 维度 | 强一致方案（2PC/XA/TCC） | 最终一致方案（消息、SAGA） |
|------|--------------------------|---------------------------|
| 数据状态 | 任何时刻全局一致 | 中间有不一致窗口 |
| 用户体验 | 同步等待结果 | 异步通知（如"处理中"） |
| 实现复杂度 | 高 | 中 |
| 典型场景 | 资金账务、库存强管控 | 订单异步流转、积分、通知 |

**判断标准**：业务能否接受"短暂不一致"。转账必须强一致；下单后几秒才加积分，用户完全无感，用最终一致即可。

### 性能 vs 可靠性

- 同步方案（2PC、TCC）一致性更强但性能差：同步等待、资源锁定，TPS 显著下降；
- 异步方案（消息表、事务消息）吞吐高，但引入重试、幂等、对账等补偿机制，需要保证最终可达；
- 经验：核心链路的写操作能异步化就异步化（MQ 削峰 + 事务消息保可靠），把同步等待留给必须即时反馈的环节。

### 业务侵入性

| 方案 | 侵入程度 | 说明 |
|------|----------|------|
| XA / Seata AT | 无侵入 | 框架/数据库层完成，业务代码零改造 |
| 事务消息 / 本地消息表 | 低~中 | 需要发送方改造消息发送逻辑、消费方保证幂等 |
| SAGA | 中 | 每个步骤要设计补偿逻辑 |
| TCC | 高 | 每个服务三个接口，还需处理空回滚/悬挂/幂等 |

**总体原则**：

1. **能不用分布式事务就不用**：优先通过业务设计规避（合并服务、调整操作顺序、用最终一致的业务补偿）；
2. 从低侵入方案开始尝试：AT → 消息事务 → SAGA → TCC → XA，按一致性需求和性能预算逐级升级；
3. 无论选哪种方案，**幂等和重试兜底（对账）都是标配**。
