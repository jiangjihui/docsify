# 线上接口负载剧增，快扛不住了，如何处理

> 第一动作**不是加缓存、不是加节点**，而是**先定位瓶颈在哪**。缓存只在「读密集 + 数据可缓存」时才是最优解，加错位置等于白忙活。本文结合完整压测定位实践，给出「先看监控 → 三分法定位 → 对症处置」的工程化流程。

## 1. 先看监控：4 个指标定方向

出问题时第一眼看这 4 个指标（Prometheus / Grafana / Spring Boot Actuator 都能拿到），每个读数指向不同方向：

| 指标 | 危险阈值 | 读数含义 |
|------|---------|---------|
| `tomcat.threads.busy` | 持续贴 `maxThreads`（默认 200） | 线程池满，请求在排队 |
| `hikaricp.connections.pending` | > 0 持续出现 | DB 连接池满，请求在等连接 |
| `jvm.gc.pause` | >100ms 频繁出现 | GC 停顿吞 CPU |
| `process.cpu.usage` | > 80% 持续 | 系统级 CPU 不够 |

**读数组合判读**：

- `busy` 贴 200 + `pending` 为 0 → 应用本身处理慢（CPU/算法）
- `busy` 贴 200 + `pending` > 0 → DB 连接池是瓶颈
- `pending` > 0 但 `busy` 不高 → Tomcat 有空线程，只是拿不到 DB 连接
- `gc.pause` 高 → 看 [生产服务器变慢诊断](生产服务器变慢诊断.md) 的 GC 路径
- 4 个都正常但 RT 高 → 下游依赖慢（DB 慢查询、HTTP 调用慢）

> 没有监控？立刻补：`management.endpoints.web.exposure.include=health,metrics,prometheus`，见 [SpringBoot 默认配置的隐藏陷阱](/实践/性能工程/SpringBoot默认配置的隐藏陷阱.md) 第 6 条。

## 2. 瓶颈三分法

读完监控，90% 的情况落到这三个分支之一：

```
接口 RT 高
  │
  ├── tomcat.threads.busy 贴满  →  [分支A] 应用本身慢
  │
  ├── hikaricp.pending > 0     →  [分支B] DB 连接池排队
  │
  └── 以上都正常但下游 RT 高    →  [分支C] 外部依赖慢
```

### 分支 A：应用本身慢

**现象**：线程池打满，但 DB 连接池空闲 → 线程都在跑业务代码。

**定位**：抓 jstack 看 RUNNABLE 的业务线程栈帧（完整 4 步法见 [CPU 飙升定位](CPU飙升定位Java代码.md)）。

**处置**：

- 算法/O(N²) 热点 → 优化代码
- 线程池太小 → 调 `server.tomcat.threads.max`，**但要先看下游**：线程池调到 400 但 DB 连接池仍 10，等于把排队从 Tomcat 搬到 DB 连接池。公式：`threads = 目标 TPS × 单请求耗时 ms / 1000`，详见 [SpringBoot 默认配置的隐藏陷阱](/实践/性能工程/SpringBoot默认配置的隐藏陷阱.md) 第 1、2 条

### 分支 B：DB 连接池排队

**现象**：`hikaricp.connections.pending` > 0，Tomcat 大量线程 WAITING。

**定位**：

```bash
# 看 SQL 慢查询（MySQL）
SHOW PROCESSLIST;
# 或查 information_schema
SELECT * FROM information_schema.processlist
WHERE command != 'Sleep' AND time > 1 ORDER BY time DESC;
```

**处置**：

- 慢 SQL → 加索引 / 改查询，见 [SQL 优化](/实践/数据库/SQL优化.md)
- 连接池过小 → 调 `spring.datasource.hikari.maximum-pool-size`，但要确认 DB 实例连接上限（Holo / MySQL 都有上限），留 30~50% 余量给其他服务
- 事务过长 → 缩小事务范围、避免大事务

**真实案例**：TPS 卡在 46 不再增长，最终定位到 HikariCP 默认 10 连接 × 单查询 200ms = 50 TPS 上限——正好卡死，调整到 30 连接后突破。

### 分支 C：外部依赖慢

**现象**：应用指标全正常，但整体 RT 高；查下游服务响应慢 / 网络 RT 高。

**定位**：链路追踪（SkyWalking / Zipkin / Spring Cloud Sleuth），找最慢的 span。

**处置**：

- 下游接口响应慢 → 推动对方优化 / 加熔断降级（Sentinel / Resilience4j）
- 网络 RT 高 → 检查跨地域调用、DNS 解析慢
- 第三方 API 限流 → 加本地缓存（此时才轮到缓存）

## 3. 应急 vs 根治

**应急（分钟级）**：限流 → 降级 → 临时扩容 → 加缓存（只读场景）。目标是先让服务活下来。

**根治（小时/天级）**：压测找上限 → 调参 → 改造 → 回归验证。目标是让瓶颈消失。

**压测找上限**：JMeter 阶梯加压，看吞吐拐点在哪（完整实操见 [SpringBoot 默认并发上限压测](/实践/性能工程/SpringBoot默认并发上限压测实践.md)）。

## 4. 缓存的正确打开方式

**缓存适合**：读多写少、数据可容忍短暂过期、查询本身慢（DB 聚合 / 远程调用）。

**缓存不适合**：
- 强一致性要求 → 缓存穿透 / 击穿 / 雪崩会让事情更糟
- 写多读少 → 缓存命中率低，白占内存
- 数据本身查询就快（走索引的主键查询） → 加缓存是负优化

**加缓存的正确姿势**：
1. 先压测确认瓶颈是「读密集」
2. 选合适缓存粒度（整页 / 单接口 / 单字段）
3. 设合理 TTL（太长数据陈旧，太短缓存失效）
4. 监控缓存命中率（<80% 说明没命中，调）

→ 详见 [Redis](/contents/storage/Redis.md)
