# 生产环境服务器变慢，如何诊断处理

> 服务器变慢 ≠ CPU 高。**先分诊再深查**——用 `top` 一眼定四路，每条支路有对应工具链。本文把「变慢」拆成 4 种独立症状，每条都给命令 + 输出解读。

## 速查：top 一眼分诊

```bash
# -bn1 快照，关键看 us/sy/wa/id/st 五列
top -bn1 | grep '%Cpu'
```

| top 输出 | 症状 | 跳转 |
|---------|------|------|
| `us` 高（>70%） | CPU 计算密集 | [CPU 高](#1-cpu-高) |
| `us` 低但 `load average` 高 | 上下文切换/锁竞争 | [CPU 低 + load 高](#2-cpu-低-load-高) |
| `wa` 高（>20%） | I/O 等待 | [I/O 等待高](#3-iowait-高) |
| `used` 接近 `total`，`swap used` 高 | 内存不足 | [内存瓶颈](#4-内存瓶颈) |

## 1. CPU 高

`us`（用户态 CPU）长期 >70% 说明进程在密集计算——大概率 Java 线程在做重活（GC、JIT、业务逻辑）。

**定位到业务线程**：走 [CPU 飙升定位到 Java 代码](CPU飙升定位Java代码.md) 的 4 步法（top → ps -mp → printf → jstack），本篇不再重复。

**定位到 GC 线程**：

```bash
# 看 JVM GC 情况：YGC 次数/耗时、FGC 次数
jstat -gcutil <PID> 1000 5
# 输出关键列：S0/S1/Eden/Old/Metaspace 占用%；YGC/YGCTS/FGC/FGCT
```

| 指标 | 含义 | 危险阈值 |
|------|------|---------|
| YGC（秒） | Young GC 耗时 | 每次 >100ms 要警惕 |
| FGC 次数 | Full GC 次数 | >0 就危险 |
| FGCT（秒） | Full GC 累计耗时 | >1s 用户体感卡顿 |
| O（Old 区%） | 老年代占用 | >80% 持续触发 GC |

→ 深入见 [容器与 JVM 内存配置不一致致 OOMKiller](/实践/产线故障复盘/md/pod重启/容器与JVM内存配置不一致致OOMKiller.md)

## 2. CPU 低，load 高

`load average` 持续 >CPU 核数 × 2，但 `us` 不高——典型症状：**上下文切换风暴**。

```bash
# 看 cs（上下文切换/sec）和 in（中断/sec）
vmstat 1 10
# 关键列：cs 持续 >10000，in 持续高
```

```bash
# 看哪些线程在频繁切换（每个线程的 csw 上下文切换数）
pidstat -w -p <PID> 1 5
# 输出关键列：cswch/s（自愿切换）、nvcswch/s（非自愿切换）
```

**处置思路**：
- `nvcswch/s` 高 → 线程被 CPU 时间片抢占 → 线程数过多 / CPU 超售
- `cswch/s` 高 → 线程主动让出（等锁、等 IO）→ 锁竞争 / IO 慢

→ 锁竞争排查用 `jstack` 看大量 BLOCKED 的线程；IO 慢跳转 [I/O 等待高](#3-iowait-高)

## 3. iowait 高

`wa`（iowait）长期 >20% 说明 CPU 在等磁盘/网络 IO。

```bash
# 看每个设备的 %util、await
iostat -x 1 5
# 关键列：%util（磁盘饱和度）、await（平均等待 ms）、r/s w/s（每秒读写次数）
```

| 指标 | 含义 | 危险阈值 |
|------|------|---------|
| %util | 磁盘忙碌时间占比 | >80% 饱和 |
| await | IO 平均耗时 ms | HDD >20ms、SSD >5ms 异常 |
| r/s + w/s | 每秒 IO 次数 | 远大于硬件额定 → 过载 |

**进程级定位**：

```bash
# 看每个进程的磁盘读写（需 sudo）
pidstat -d -p <PID> 1 5
# 或 iotop（更直观，需 root 与内核支持）
iotop -oP <PID>
```

**常见根因**：
- 日志写入风暴（日志级别突然 DEBUG、同步写盘）→ 改异步日志
- 数据库慢查询（大结果集、全表扫）→ 查 [SQL 优化](/实践/数据库/SQL优化.md)
- 第三方依赖落盘频繁（MQ 本地 checkpoint、Redis AOF）→ 改异步 / 降频

**间接诊断法**：负载增大时吞吐量不能线性提升、CPU 不能线性增长——很可能 IO 阻塞把进程卡住。

## 4. 内存瓶颈

```bash
# 看系统级内存（Linux 3.14+）
free -h
# 关键看：used / available / swap used
```

| 字段 | 含义 | 陷阱 |
|------|------|------|
| **available** | 应用真正可用内存 | 不要看 free，Linux 会把空闲内存用于缓存 |
| **used** | 已用（不含缓存） | >80% 要警惕 |
| **swap used** | 已用交换分区 | >0 即已开始换出，性能骤降 |

**JVM 专项**（`free` 显示 used 高但 swap 为 0 时，先怀疑 JVM 吃光了）：

```bash
# 看 JVM 堆内存分布
jmap -heap <PID>
# 输出关键段：Heap → Eden / Survivor / Old / Metaspace 的 used / capacity

# 看对象直方图（占内存最多的类 Top 20）
jmap -histo <PID> | head -25
```

**dump 大堆内存分析**（生产慎用，会暂停应用）：

```bash
# dump 堆到文件（文件会很大，-F 强制 dump 已挂起的进程）
jmap -dump:live,format=b,file=heap.hprof <PID>

# 用 MAT (Eclipse Memory Analyzer) 分析，看 Leak Suspects 报告
```

**堆外内存排查**（`jmap -heap` 显示堆正常但 RSS 持续涨）：

```bash
# 看进程整个虚拟内存映射，找大段匿名映射
pmap -x <PID> | sort -nk3 -r | head -20
# 关键列：RSS（实际驻留）大的段、地址在 heap 之上的段

# 或看 JVM NativeMemoryTracking（需启动时 -XX:NativeMemoryTracking=detail）
jcmd <PID> VM.native_memory summary
```

## JVM GC 日志（深度排查）

当 `us` / `wa` / `load` 都看不出明显异常，但业务响应慢时，可能是 GC 停顿在作怪。

**开启 GC 日志**（应用启动参数加）：

```bash
# JDK 8（CMS）
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/to/gc.log

# JDK 11+（G1/ZGC，统一日志）
-Xlog:gc*:file=/path/to/gc.log:time,uptime,level,tags
```

**分析 GC 日志**：

```bash
# 看用户线程总暂停时间
grep "pause" gc.log | awk '{print $X}'
# 或用 GCEasy (https://gceasy.io) 上传日志可视化
```
