# SNAPSHOT与mvn-install覆盖本地仓库

> **故障日期**: 2025-07-31
> **涉及服务**: 业务服务A、多个依赖方
> **故障类型**: 依赖异常

## 故障现象
业务测试环境和 UAT 环境引用的业务服务A 的 1.7.4.20250617-2-snapshots 版本（SNAPSHOT）二方库依赖，业务方在使用时发现依赖内容发生了变化——之前存在的枚举现在缺失了。

每次业务服务A 发布上线时，这个依赖的版本包内容都会被更新为最新内容，但版本号保持不变，导致下游依赖方拉到的"同一个版本"实际对应不同时刻的代码。

## 现场分析
项目发布共用同一台 jenkins 服务器，且发布流程统一使用 `mvn install` 命令。当 A 服务依赖 B 服务的某个版本（例如 1.1 版本）时，如果该版本已经存在于 jenkins 服务器的本地 maven 仓库中，maven 就不会再去远程仓库拉取，而是直接复用本地仓库中的内容。

当业务服务A 新增了指标枚举，但 pom 文件中的版本号并未修改（仍是 1.1 版本）时，只要业务服务A 触发发布，jenkins 服务器本地仓库中该版本的依赖内容就会被新打包的产物覆盖，而版本号保持不变。`mvn install` 会执行编译、打包并把产物安装到本地仓库；`mvn package` 只执行编译、打包，不会安装到本地仓库。

其他项目如果也引用了同一个版本（1.1 版本）的依赖，构建时就会从本地仓库拿到被最新修改覆盖过的代码，而非最初以 1.1 版本打包发布时的代码，从而出现"版本号没变但内容变了"的漂移现象。

## 根因
根因是 SNAPSHOT 版本 + mvn install + jenkins 服务器共用三者叠加：本地仓库内容被覆盖但版本号不变，使其他项目拉取到最新代码而非原打包代码。

SNAPSHOT 版本在 maven 语义中本身允许内容漂移（远端与本地可不一致），叠加 `mvn install` 把每次发布的新产物写入本地仓库，再叠加 jenkins 服务器跨项目共用同一份本地仓库，最终导致：只要业务服务A 发布，所有依赖该版本的其他项目在下次构建时都会拿到被覆盖后的最新内容，而版本号未变，调用方无法通过版本号识别内容变化。

## 解决方案
- 生产环境依赖固定版本号，不使用 SNAPSHOT 版本，发布时打 release 版本。
- 发布流程改用 `mvn package` 而非 `mvn install`，避免产物写入本地仓库污染其他项目。
- jenkins 服务器按项目/团队隔离，避免本地仓库跨项目共用。
- 依赖方在 pom 中明确指定 release 版本，不直接引用 SNAPSHOT。
- 业务服务A 新增/修改枚举或接口时，必须同步升级 pom 版本号，确保内容变更可被版本号识别。

## 复盘要点
- SNAPSHOT 版本内容会漂移，不应在生产依赖中使用。
- mvn install 与 mvn package 的区别：前者打包并安装到本地仓库，后者只打包不安装。
- jenkins 服务器共用会放大依赖内容覆盖问题。
- 依赖方应明确指定 release 版本，避免拉到漂移内容。
- 二方库内容变更必须同步升级版本号，避免版本号不变但内容变化。

## 关键命令与指标
```bash
# mvn install：打包并安装到本地仓库（会覆盖原版本内容）
# mvn package：只打包，不安装到本地仓库
# mvn dependency:tree：查看依赖树，定位传递依赖
# 关键指标：
#   漂移版本：1.7.4.20250617-2-snapshots（SNAPSHOT）
#   示例版本：1.1（pom 未升级，内容已被覆盖）
```
