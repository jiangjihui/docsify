# 创建型 - 生成器模式(Builder pattern)

生成器模式（Builder Pattern）也叫建造者模式，它将一个复杂对象的**构建过程**与它的**表示**分离，使得同样的构建过程可以创建出不同的表示。

当一个对象有大量可选字段、构造参数很多，或者对象内部结构复杂时，直接写构造函数会非常痛苦（参数顺序容易搞错、可读性差），生成器模式通过"分步设置 + 最后统一构建"来优雅地解决这个问题。

## 解决的问题

1. **构造参数过多**：一个类有十几个字段，构造函数参数列表很长，调用方难以分清每个参数含义（Telescoping Constructor 反模式）；
2. **可选参数场景**：很多字段是可选的，被迫写多个重载构造函数或传大量 `null`；
3. **不可变对象**：希望对象创建后不可变（字段 final），但一次性传全参数又很繁琐；
4. **复杂构建步骤**：对象内部需要多步组装或校验，希望把这些步骤封装起来复用。

## 结构

| 角色 | 职责 |
|------|------|
| **Product（产品）** | 被构建的复杂对象 |
| **Builder（抽象建造者）** | 定义构建步骤的抽象接口（如 setXxx / build） |
| **ConcreteBuilder（具体建造者）** | 实现各构建步骤，并持有最终产品的组装逻辑 |
| **Director（指挥者）** | （可选）按固定顺序调用构建步骤，可省略，由客户端直接驱动 Builder |

## 代码示例

经典写法（以构建一台电脑为例）：

```java
// Product：产品
public class Computer {
    private final String cpu;    // 必选
    private final String ram;    // 必选
    private final boolean ssd;   // 可选
    private final boolean gpu;   // 可选

    private Computer(ComputerBuilder builder) {
        this.cpu = builder.cpu;
        this.ram = builder.ram;
        this.ssd = builder.ssd;
        this.gpu = builder.gpu;
    }

    public static class ComputerBuilder {
        private final String cpu;   // 必选字段放构造
        private final String ram;   // 必选字段放构造
        private boolean ssd = false;
        private boolean gpu = false;

        public ComputerBuilder(String cpu, String ram) {
            this.cpu = cpu;
            this.ram = ram;
        }

        public ComputerBuilder withSsd(boolean ssd) {
            this.ssd = ssd;
            return this;   // 返回 this 支持链式调用
        }

        public ComputerBuilder withGpu(boolean gpu) {
            this.gpu = gpu;
            return this;
        }

        public Computer build() {
            // 可在这里做参数校验
            if (cpu == null || ram == null) {
                throw new IllegalArgumentException("cpu/ram 为必选参数");
            }
            return new Computer(this);
        }
    }

    @Override
    public String toString() {
        return "Computer{cpu=" + cpu + ", ram=" + ram + ", ssd=" + ssd + ", gpu=" + gpu + '}';
    }
}
```

客户端使用：

```java
Computer computer = new Computer.ComputerBuilder("i7-13700K", "32G")
        .withSsd(true)
        .withGpu(true)
        .build();
```

> 现代 Java 开发中，Lombok 的 `@Builder` 注解可以自动生成这套样板代码，日常业务开发直接用注解即可；在框架/工具类库中，手写 Builder 仍很常见（如 OkHttp 的 `Request.Builder`、Retrofit 的配置类）。

## 与工厂模式的区别

| 维度 | 工厂模式 | 生成器模式 |
|------|---------|-----------|
| 关注点 | 创建**哪个**对象（产品类型选择） | 如何**一步步组装**一个复杂对象 |
| 粒度 | 通常一步创建，返回完整产品 | 分步设置属性，最后 build 组装 |
| 场景 | 对象构造简单、创建逻辑需要集中管理 | 对象字段多/可选、构造复杂 |
| 结果 | 不同工厂产出不同类型对象 | 同一构建过程产出不同配置的同类型对象 |

一句话：**工厂模式解决"创建谁"的问题，Builder 解决"怎么组装"的问题。**

## 适用场景

- 对象字段多且有大量可选参数（避免超长构造函数）；
- 需要构造不可变对象（字段 final，通过 Builder 传入）；
- 构建过程有参数校验或默认值逻辑，希望集中管理；
- 链式 API 设计（如 OkHttp Request、StringBuilder）。

## 优缺点

**优点**：
- 调用方可读性好，参数语义清晰；
- 与不可变对象配合良好；
- 可复用同一构建过程产出不同配置。

**缺点**：
- 类数量增加（每个产品都要配套 Builder）；
- 若字段少且必填，用 Builder 反而过度设计，直接构造函数或静态工厂更简单。
